# 설계 결정 기록 (Decision Log)

면접에서 "왜 이렇게 했나요?"에 답할 수 있도록, 결정마다 **맥락 → 결정 → 근거 → 대안/트레이드오프**를 남긴다.
수치 근거는 `reports/data_audit.md`에 있다.

## D1. 학습/검증/테스트 분할: 시즌 단위, 테스트는 2025와 2026을 따로 보고

- **맥락**: 명세는 `match_id` 단위 분할만 요구한다. 하지만 팀 강도 피처가 '과거 경기'에 의존하므로, 무작위 분할을 하면 미래 경기로 학습해 과거를 맞히는 구성이 섞인다. 날짜 컬럼은 없고 시즌(폴더)만 확실하다.
- **결정**: train = 2021–2023, valid = 2024(확률 보정·하이퍼파라미터), test = **2025와 2026을 각각** 평가한다. 모든 분할은 경기 단위로 겹치지 않는다(시즌 분할이면 자동으로 보장되고, 테스트 코드로도 검증한다).
- **근거**:
  - 실제 서비스는 "과거로 학습해 다음 시즌을 예측"하는 상황이다. 시간순 분할이 이 상황과 가장 비슷하다.
  - 2026은 `Loadout Value`가 전부 결측이고 2025는 대부분 있다. 테스트를 둘로 나누면 **장비가치 없이도 모델이 버티는지**를 따로 측정할 수 있다.
- **트레이드오프**: 2023년부터는 1부 리그만 있어서 train(2·3부가 많음)과 test(1부)의 분포가 다르다. 성능이 낮게 나올 수 있지만, 이것이 더 정직한 추정이다. 대회 순서표(`data/reference/tournament_order.csv`)가 준비되면 시즌 안에서도 대회 단위로 더 세밀하게 나눌 수 있다.

## D2. Team A/B 정의와 좌우 반전 증강

- **결정**: A/B는 `scores.csv`의 Team A/B를 따른다. 학습 시에는 A↔B를 뒤집은 복사본을 추가한다(라벨도 반전).
- **근거**: A/B 배정이 무작위가 아니면(예: 상위 시드가 A) 모델이 "A라서 이긴다"는 가짜 신호를 배운다. 증강하면 `P(A 승) + P(B 승) = 1`인 대칭성이 학습 데이터 수준에서 보장된다.
- **주의**: 증강은 **분할 이후** train에만 적용한다. 분할 전에 하면 같은 라운드의 원본과 반전본이 train/test에 나뉘어 누수가 생긴다.

## D3. 공격/수비 진영 피처 추가 + `/api/predict`에 `team_a_side` 필드 추가

- **맥락**: 명세는 진영 정보가 없다고 가정했다. 감사 결과, `maps_scores`의 Attacker/Defender 컬럼은 실제로 전·후반 점수였다. 대신 라운드 승리 방식으로 진영을 역산할 수 있고, 하프의 88–95%에서 진영이 확정된다.
- **결정**: `rounds.team_a_side`(atk/def/NULL)를 적재하고 피처로 쓴다. 이 피처를 쓰려면 예측 요청에도 필요하므로 `/api/predict`에 `team_a_side`(선택 필드, 생략 시 NULL)를 추가한다. 명세 §6 대비 변경이며 사용자 승인을 받았다.
- **누수 방지**:
  - 진영 자체는 라운드 시작 전에 공개된 정보라서 써도 된다. 하지만 **진영을 알아냈는지 여부**는 라운드 결과(승리 방식)에 의존하므로 결측 여부를 피처로 쓰지 않는다.
  - 하프 단위 전파로 결측을 최소화한다.
  - `win_method`는 절대 피처로 쓰지 않는다.

## D4. `rounds`는 win_loss 기준으로 전 라운드를 적재하고, 이코노미는 NULL 허용

- **근거**: `eco_rounds`는 맵의 46–100%만 담고 있다. 스코어·연승·최근 3라운드 승률은 앞 라운드가 하나라도 빠지면 틀어진다. 그래서 라운드 시퀀스는 완전한 소스(win_loss)로 만들고 eco는 붙인다. 학습 표본은 `buy_type IS NOT NULL`인 라운드로 거른다.

## D5. 스키마 변경 (명세 §4 대비)

`src/propredict/models.py`의 모듈 docstring에 항목별 이유를 적었다. 요약하면 다음과 같다.
- 원본 ID(`source_match_id`, `source_game_id`)를 보존해 추적성을 확보했다.
- 진영 컬럼과 `win_method`(분석 전용)를 추가했다.
- `idx_rounds_map_game`을 제거했다. `UNIQUE(map_game_id, round_number)`가 이미 같은 선두 컬럼 인덱스를 제공하기 때문이다.
- 범주형 컬럼은 PostgreSQL ENUM 대신 CHECK 제약을 썼다. 값 변경 마이그레이션이 더 쉽다.

## D6. 복합키 충돌 2건은 삭제가 아니라 제외

- **근거**: 명세는 "중복 2건"이라고 했지만 Match ID가 서로 다른 두 경기다. `eco_rounds`에는 Match ID가 없어 두 경기의 라운드를 구분할 수 없다. 한쪽을 임의로 남기면 틀린 데이터가 들어간다. 제외하고 건수를 ETL 요약에 출력한다.

## D7. 마이그레이션은 API 컨테이너 시작 시 자동 적용

- **근거**: 완료 기준이 "`docker compose up` 한 번으로 전체 스택이 뜬다"이다. `alembic upgrade head`는 이미 최신이면 아무 일도 하지 않으므로 매번 실행해도 안전하다.
- **트레이드오프**: API 레플리카가 여러 개면 동시 실행 경쟁이 생길 수 있다. 이 프로젝트는 단일 인스턴스라서 수용한다(운영 규모라면 별도 migrate job으로 분리).

## D8. 모델은 API 시작 시 1회 로드 (lifespan)

- **근거**: 요청마다 디스크에서 모델을 읽으면 I/O 때문에 "입력 변경 후 500ms 내 갱신" 목표를 지키기 어렵다. 모델 파일은 `artifacts/`를 읽기 전용으로 마운트해, 이미지를 다시 빌드하지 않고 교체한다.

## D9. 단일 Python 프로젝트(src 레이아웃)로 ETL·모델·API 공유

- **근거**: 학습 때 쓴 피처 생성 코드를 서빙에서 **복사하지 않고 import**한다. 두 곳에 같은 로직이 있으면 조금씩 어긋나며 생기는 training-serving skew를 막을 수 있다.

## D10. ETL은 시즌 단위 '동기화' (COPY → upsert → 사라진 행 삭제, 한 트랜잭션)

- **맥락**: 완료 기준은 "ETL이 멱등적으로 동작한다"이다. 가장 쉬운 방법은 시즌을 통째로 지우고 다시 넣는 것이다.
- **결정**: 스테이징 임시 테이블에 COPY → 본 테이블에 `INSERT … ON CONFLICT DO UPDATE … WHERE (값) IS DISTINCT FROM (새 값)` → 원본에서 사라진 행 DELETE. 시즌마다 별도 트랜잭션으로 처리한다.
- **근거**:
  - 지우고 다시 넣으면 `match_id` 같은 **대리키가 실행마다 바뀐다**. API URL(`/api/matches/{id}`)과 저장된 예측 결과가 깨진다. upsert는 키를 유지한다(재실행 전후 키 해시 동일로 확인).
  - `IS DISTINCT FROM` 조건 덕분에 같은 데이터로 재실행하면 "삽입 0 · 갱신 0 · 삭제 0"이 나온다. 이 출력이 곧 멱등성의 증거다.
  - `RETURNING (xmax = 0)`으로 삽입과 갱신을 구분해 센다(PostgreSQL에서 새로 삽입된 행은 xmax가 0).
  - COPY는 행 단위 INSERT보다 빠르다. 56만 라운드 전체 적재가 약 2분 걸린다.
  - 시즌 단위 트랜잭션이라 중간에 실패해도 절반만 적재된 상태가 남지 않는다.
- **트레이드오프**: 스테이징 SQL이 ORM보다 길다. 대신 적재 경로가 SQL 한 곳에 모여 있어 동작을 설명하기 쉽다.

## D11. 경기 자연키 컬럼 NOT NULL (마이그레이션 0002)

- **근거**: upsert는 `UNIQUE(season, tournament, stage, match_type, match_name)`에 의존한다. 그런데 PostgreSQL의 UNIQUE는 NULL끼리를 서로 다른 값으로 본다. 키에 NULL이 하나라도 있으면 `ON CONFLICT`가 발동하지 않아 재실행마다 같은 경기가 새로 쌓인다. 원본 전체에 결측이 없음을 확인한 뒤 스키마 수준에서 막았다(`NULLS NOT DISTINCT`보다 의도가 분명하다).

## D12. 진영은 '맵 단위 투표'로 역산

- **근거**: 결정적 라운드(폭발/해체/무설치 시간종료) 하나하나를 하프·연장 교대 규칙으로 "전반 공격팀은 누구였나"로 환산해 투표한다. 표가 하나로 모이면 맵 전체 라운드의 진영이 정해진다. 하프 단위(감사 시 88–95%)보다 커버리지가 크게 올라 **라운드의 99.27%**에서 진영을 알 수 있다.
- **안전장치**: 표가 엇갈리면 추측하지 않고 NULL로 둔다. 역산한 진영으로 계산한 맵별 공격 승률이 47–53%로 대칭이라는 점이 방향이 맞다는 근거다(`reports/etl_summary.md` §3.2).

## D13. 시간 순서 = (시즌, 원본 Match ID)

- **맥락**: 팀 강도는 '과거 경기까지만' 집계해야 하는데 원본에 날짜가 없다.
- **결정**: 시즌(폴더) 안에서는 vlr.gg 원본 Match ID 오름차순을 시간 순서로 쓴다.
- **근거**: 같은 팀이 한 대회에서 치른 경기 쌍을 대진표 단계로 비교했다. 8강 → 4강 → 결승 순서가 ID 순서와 96.2% 일치했고(8,487쌍), 스위스 라운드 1 → 2 → 3은 98.9% 일치했다(1,246쌍). 완벽하지 않은 만큼, 시즌 경계를 넘는 분할(D1)로 테스트셋 누수는 원천 차단했다. 시즌 안의 순서 오차는 팀 강도 피처의 잡음으로만 작용한다.

## D14. 학습 데이터 장비가치 25% 마스킹

- **맥락**: 2026년은 `Loadout Value`가 전부 결측인데, 학습 데이터(2021–23)에는 결측이 없다. LightGBM은 학습 때 본 적 없는 결측을 임의의 분기로 보낸다.
- **결정**: train의 25% 행에서 장비가치 관련 4개 피처를 지운다. 구매유형·크레딧만으로 예측하는 경로를 배우게 하려는 것이다. A/B 반전과 마찬가지로 train에만 적용한다.
- **결과**: 2026 테스트에서도 룩업표보다 Brier가 유의하게 낮다(95% CI [−0.0021, −0.0003]).

## D15. 보정은 isotonic, valid 절반으로 / 대칭화는 기각

- valid(2024)를 경기 단위로 반씩 나눠, 한쪽은 LightGBM 조기 종료에, 다른 쪽은 isotonic 보정 학습에 쓴다. 같은 데이터를 두 번 쓰면 보정기가 이미 맞춰진 예측을 다시 학습한다.
- 보정 효과: Brier는 거의 같고(2025 0.2201 → 0.2201), ECE는 줄었다(0.0149 → 0.0070). 명세의 핵심 가치가 '확률의 신뢰성'이므로 보정 모델을 서빙한다.
- **기각한 방법**: 원본과 A/B 반전본 예측을 평균해 P(A)+P(B)=1을 강제하는 방법을 검토했다. Brier·ECE 차이가 ±0.0001로 지표 이득이 없었고, isotonic이 대칭을 다시 조금 깨서 복잡도만 늘었다. API는 P(B)를 1−P(A)로 계산하므로 응답은 항상 합이 1이다.

## D16. 하이퍼파라미터를 더 튜닝하지 않은 이유

- num_leaves {15, 31, 63} × min_child_samples {200, 500, 2000} 격자를 **valid로만** 비교했다(테스트를 보고 고르면 그것도 누수다). Brier 차이는 0.0001 이하였다.
- 해석: 병목은 모델 용량이 아니라 '라운드 시작 시점에 알 수 있는 정보의 양'이다. 라운드 결과는 에임·전술 같은 관측되지 않은 요인에 크게 좌우되고, 이 데이터에는 그런 정보가 없다. 추가 개선은 모델보다 새 정보(선수 로스터, 요원 조합 등)에서 나와야 한다.

## D17. API 설계

- **모델은 lifespan에서 1회 로드**한다. 모델 파일이 없어도 앱은 뜨고(통계 엔드포인트는 동작), 예측만 503을 돌려준다. DB 연결 실패는 스택트레이스 대신 503으로 응답한다.
- **피처는 학습 코드를 그대로 import**한다(`state_features`, `sequence_features`). 서빙용으로 피처를 다시 구현하지 않는다.
- **리플레이의 팀 강도는 아티팩트에서 조회**한다. 요청마다 SQL로 '이전 경기들'을 다시 집계하면 같은 로직이 두 곳에 생긴다. 그래서 학습 때 계산한 경기별 값을 원본 Match ID 키로 저장했다(재학습 결과 지표 동일 확인).
- **요청 검증**: `score_a + score_b = round_number − 1`이 아니면 422로 거부한다. 불가능한 상태로 예측하면 그럴듯하지만 의미 없는 숫자가 나온다. 학습에 없던 맵 이름도 오타 가능성이 커서 가능한 값 목록과 함께 422로 알린다.
- **top_factors**: 피처별 TreeSHAP 기여도(로그오즈 단위)다. 요청에 없어서 중립값으로 채운 모멘텀·팀 강도는 후보에서 뺀다(사용자가 넣지 않은 값이 '요인'으로 보이면 혼란스럽다).
- **명세 대비 추가**: `/api/predict`의 `team_a_side`(D3), 그리고 화면 3에서 경기를 고를 수 있게 `GET /api/matches?season=&team=` 목록을 추가했다.
- **리플레이에서 이코노미 없는 라운드는 확률을 null로 둔다.** 모델은 구매유형이 있는 라운드로만 학습했으므로 외삽하지 않는다.

## D18. 통계 쿼리 성능

- 구매유형 매트릭스: 처음 구현은 SQL에서 각 라운드를 두 관점으로 복제(UNION ALL, 42만 → 84만 행)한 뒤 집계해서 콜드 실행에 약 4초가 걸렸다. `(A 구매, B 구매)`로 한 번만 집계하면 최대 16행이 되고, 두 관점 합치기는 Python에서 해도 결과가 같다(응답 JSON 동일 확인). 약 0.13초로 줄었다.
- 맵 목록: 라운드 테이블을 조인하지 않고 ETL이 채운 `map_games.total_rounds`를 합산해 0.55초에서 16ms로 줄였다.
- 캐시를 두지 않은 이유: 위 최적화만으로 충분히 빠르고, 캐시는 ETL 재실행 후 낡은 값을 보여 줄 위험(무효화 문제)을 만든다.

## D19. 프론트엔드 상태·요청 설계

- **라운드 번호는 입력받지 않고 스코어에서 계산한다**(라운드 = A + B + 1). 둘을 따로 받으면 '14라운드인데 9:6' 같은 불가능한 조합이 생기고 API가 422로 거부한다(D17). 입력 단계에서 불가능한 상태를 만들 수 없게 했다.
- **구매유형과 장비가치를 연동한다.** 원본에서 구매유형은 장비가치 구간과 99–100% 일치한다. 슬라이더를 다른 구간으로 옮기면 구매유형 버튼이 따라 바뀌고, 버튼을 누르면 슬라이더가 그 구간의 실제 중앙값(Eco 3.6k · Semi-eco 8.1k · Semi-buy 16.7k · Full 23k)으로 이동한다. 'Eco인데 장비 30k' 같은 학습 분포 밖 입력을 막는다. 장비가치 '모름'은 null로 보낸다(2026 시즌처럼 정보가 없는 경우).
- **오래된 응답 무시**: 300ms 디바운스 후 요청을 보내고, 새 요청이 나가면 이전 요청을 `AbortController`로 취소한다. 늦게 도착한 옛 응답이 최신 결과를 덮어쓰는 경쟁 상태를 막는다. GET 화면은 `useApi` 훅 하나로 같은 규칙을 쓴다.
- **로딩 중에도 이전 결과를 유지한다.** 빈 화면이나 스피너로 바꾸지 않고 흐리게(opacity 60%) 둔다. 필터를 바꿀 때 레이아웃이 흔들리지 않는다.
- **측정**: 프로덕션 빌드에서 스코어 버튼 클릭 → 화면 갱신이 중앙값 335ms, 최대 347ms였다(12회, 디바운스 300ms 포함). 명세 기준은 500ms 이내다.
- **리플레이 기본 시즌은 2025(테스트)다.** 2021–2024는 학습·보정에 쓰인 시즌이라 그 예측은 실제보다 좋아 보인다. 이 시즌을 고르면 화면에 그렇게 안내한다.

## D20. 차트·색 설계

- **팔레트는 계산으로 검증했다.** Team A 파랑 #3987e5 / Team B 주황 #d95926은 다크 배경 대비 3:1 이상이고, 색약 시뮬레이션 색차 ΔE 26.8(기준 8 이상)이다. 빨강·초록 조합은 적록 색약에서 구분되지 않아 쓰지 않았다. 색은 `globals.css` 토큰 한 곳에만 정의한다.
- **승률 히트맵은 발산 척도**(0% 빨강 – 50% 회색 – 100% 파랑)를 OKLab `color-mix`로 연속 보간한다. 50%를 중립 회색으로 둬야 '반반'이 강조되지 않는다. 칸 안에 숫자와 표본 수를 함께 적어 색을 읽지 못해도 값을 알 수 있고, 30라운드 미만 칸(승률 표준오차 약 ±9%p)은 흐린 점선 칸으로 표시한다.
- **맵 밸런스는 50% 대비 편차로 그린다.** 공격 승률은 47–54%에 몰려 있어 0–100% 축에서는 차이가 보이지 않는다. 질문이 '어느 쪽으로 기울었나'이므로 50%를 기준선으로 놓았다.
- **신뢰구간 그림**: 룩업 대비 Brier 차이를 점 + 수염으로 그린다. 표의 소수점 넷째 자리보다 '구간이 0을 넘는가'가 한눈에 보인다.
- **접근성**: 모든 차트에 마우스·키보드 포커스 툴팁과 표 보기 전환이 있다. 계열이 2개 이상이면 범례를 항상 두고, 글자는 계열 색이 아니라 텍스트 색으로 쓴다.
- **이중 축을 쓰지 않는다.** 서로 다른 단위는 별도 차트나 표로 나눴다.

## D21. 알려진 한계: isotonic 보정의 계단 출력 (Phase 5 검증 중 발견)

- 시뮬레이터에서 스코어를 7:6 → 8:6 → 9:6 → 3:10으로 바꿔도 승률이 87.9%로 그대로였다. 원인은 isotonic 보정기다. 보정기는 **42개 값만 출력하는 계단 함수**여서 원출력이 조금 바뀌어도 같은 계단에 머문다.
- 더 큰 문제는 양 끝이다. 보정 전 확률이 0.929 이상이면 **100%**, 0.078 이하면 **0%**가 된다. 보정용 데이터(valid 절반, 8,638라운드)의 양 끝 구간에 표본이 적어 생긴 과적합이다. 라운드 승패에서 '확실'은 있을 수 없으므로 서비스 출력으로 부적절하다.
- 테스트 지표(Brier·ECE)에는 거의 드러나지 않는다. 해당 구간의 라운드가 적기 때문이다. 화면에서 입력을 직접 바꿔 보면서 발견했다.
- 해결 후보(Phase 6에서 비교 예정): ① Platt(시그모이드) 보정: 매끄럽고 0·1에 닿지 않는다. ② isotonic 결과를 원출력과 섞거나 [0.02, 0.98]로 자른다. valid 기준으로 ECE·Brier를 비교해 고른다.
